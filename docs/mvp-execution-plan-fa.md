# برنامه اجرای MVP در 8 هفته

## هفته 1: Discovery و طراحی

- نهایی سازی دامنه MVP
- طراحی User Flow اصلی
- تعریف بانک اولیه سوالات تایید شده
- طراحی Workflow تایید نسخه سوال/فرمول (Analyst -> Reviewer -> Publisher)

## هفته 2: زیرساخت و احراز هویت

- راه اندازی ریپو و CI/CD
- پیاده سازی ثبت نام، ورود، نقش ها

## هفته 3: موتور آزمون

- پیاده سازی مدل داده سوال، گزینه، پاسخ
- ساخت API های آغاز آزمون، ذخیره پاسخ، اتمام آزمون
- اضافه کردن جدول های نسخه بندی (assessment/question/weight/formula)

## هفته 4: امتیازدهی هالند و MBTI

- پیاده سازی الگوریتم امتیازدهی نسخه 1
- تولید خروجی ساختاریافته نتیجه
- پیاده سازی Sandbox فرمول و API مقایسه نسخه ها

## هفته 5: سرویس پیشنهاد

- طراحی Rule Engine اولیه
- نگاشت نتیجه آزمون به مسیرهای شغلی/تحصیلی

## هفته 6: گزارش و داشبورد

- صفحه گزارش کاربر
- داشبورد پایه مشاور
- پنل پایه تحلیل گر خبره برای ویرایش Draft و انتشار نسخه

## هفته 7: تحلیل و بهینه سازی

- رخدادنگاری قیف تکمیل آزمون
- اصلاح UX برای کاهش ریزش

## هفته 8: QA و لانچ محدود

- تست کارکردی و امنیت پایه
- انتشار بتا برای گروه محدود

## خروجی MVP

- اجرای کامل آزمون ها
- گزارش قابل اقدام
- پیشنهادهای اولیه مسیر
- پنل ساده مشاور
- پنل نسخه بندی سوال/فرمول با تاریخچه تغییرات

## ریسک های اصلی

- کیفیت پایین بانک سوالات
- تفسیر بیش از حد قطعی نتایج
- ریزش در میانه آزمون به دلیل طولانی بودن

## راهکار کاهش ریسک

- بازبینی علمی توسط متخصص
- گزارش توضیح پذیر و غیرقطعی
- نسخه کوتاه اولیه + نسخه کامل اختیاری

## یادداشت انتشار فاز A (کیفیت آزمون و مسیر اعتبارسنجی)

ترتیب انتشار پیشنهادی:

1. **Migration دیتابیس**
   - اجرای migration جدید `20260709_02` برای جدول `version_validation_reports`.
2. **استقرار API**
   - انتشار API شامل:
     - Quality report سوالات
     - Gateهای انتشار نسخه سوال/فرمول
     - ذخیره گزارش اعتبارسنجی
3. **فعال سازی CI Gateها**
   - اجباری شدن suiteهای کیفیت (scoring / formula / phase2-3 / reports) در CI.
4. **استقرار Web**
   - انتشار adapter قرارداد `assessment.service` برای استفاده از endpointهای canonical (`/sessions/*`) با fallback کنترل‌شده.

ریسک های وابستگی بین فازی:

- **وابستگی Web به endpointهای سازگاری:** این ریسک با پشتیبانی native مسیر `combined` روی قرارداد canonical (`/sessions/*`) رفع شد؛ fallback فقط برای خطای عدم‌دسترسی backend نگه داشته می‌شود.
- **وابستگی داده تاریخی به Gateهای سخت‌گیرانه:** نسخه هایی که قبلا منتشر شده‌اند ممکن است با قواعد جدید ناسازگار باشند؛ Gateها فقط روی publish جدید enforce می‌شوند.
- **وابستگی CI به محیط:** اجرای lint/test وب نیازمند `NEXTAUTH_SECRET` و `NEXTAUTH_URL` است (مانند پیکربندی workflow).

### یادداشت قرارداد Runtime (Phase D)

از این فاز، قرارداد canonical مسیرهای زیر برای `holland`، `mbti` و `combined` یکسان است:

- `POST /sessions/start`
- `POST /sessions/{id}/answers`
- `POST /sessions/{id}/complete`
- `GET /sessions/{id}/result`

در حالت `combined`، backend یک session واحد با سوالات هر دو آزمون برمی‌گرداند و خروجی نتیجه شامل بخش‌های تفکیک‌شده `holland` و `mbti` است تا وب بدون مسیر mock اختصاصی اجرا شود.
